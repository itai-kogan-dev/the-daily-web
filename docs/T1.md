# T1 - the public site

What the public side of the site is, the calls that went into building it, and
what is still someone else's job. `docs/API.md` is the contract; this is the
reasoning behind it and a note of where the implementation lives.

Branch: `t1/public-site`, off `t2/reporter-workspace`. It cannot be based on
`main`, which is still just a `.gitignore` - the models, the session middleware
and the image store all arrived with the phase 0 skeleton and the reporter work.

## What is done

| Endpoint | Where | Notes |
|---|---|---|
| `GET /` | `controllers/publicController.js` `feedPage` | Rendered on the server. Works with JavaScript off. |
| `GET /article/:id` | `publicController.articlePage` | Whole article in the HTML. Counts a view. 404 for anything not live. |
| `GET /api/articles` | `publicController.listArticles` | `page`, `q`, `category`, `sort=date\|popular`. `q` matches part of a word in the title or summary. |
| `GET /api/articles/:id/comments` | `publicController.listComments` | Most recent 100, oldest first. |
| `POST /api/articles/:id/comments` | `publicController.addComment` | Rate limited to 3 a minute, already wired in `routes/public.js`. |

Not done, and why:

- `GET /api/weather` is still the `todo()` stub. `docs/API.md` lists it under
  T1 but `.env.example` labels the key "T4 - sidebar weather widget", so T4 owns
  it. The sidebar keeps its placeholder. See the open question below.
- The feed and article pages are the only T1 pages. Nothing else in
  `routes/public.js` is left unimplemented.

## Files

New:

- `controllers/publicController.js` - every read and the comment write.
- `services/viewCounter.js` - the 5 minute bucket increment.

Changed:

- `routes/public.js` - five `todo()`s replaced.
- `views/feed.ejs`, `views/article.ejs` - were stubs.
- `public/js/feed.js`, `public/js/article.js` - were stubs.
- `public/css/main.css` - was "layout skeleton and shared tokens only".

Deliberately not touched: `middleware/*`, the auth/reporter/editor/analytics
routes, `services/imageStore.js`, `scripts/seed.js` and `views/partials/*`.
`public/css/reporter.css` exists so T1 and T2 are not editing the same
stylesheet, so the new rules went into `main.css` under `feed-`, `article-`,
`comment-` and `chip` names and reuse nothing from `reporter.css`.

The one model change is a comment on the `publishedContent.title` text index,
which the feed search no longer uses. See the search decision below.

## Decisions

**The feed filters on `isLive`, not on `status`.** `docs/API.md` says `/api/
articles` "returns published articles only", which reads like `status:
'published'`. That would hide an article from readers the moment a reporter
starts editing it, and `docs/DECISIONS.md` says explicitly that such an article
"is `isLive: true` and `pending_editor` at the same time, and it has to stay in
the feed". The decisions log wins, because it is the document that explains
itself. Anyone reading the API table cold should read that line as "reader
visible".

**Search matches part of a word, so it uses a regex and gives up the text
index.** `models/Article.js` declares a text index on `publishedContent.title`,
but `$text` only ever matches whole words, and searching for `por` to find
"port" and "transport" is worth more than the index. No index can serve a
substring, so `q` becomes a case-insensitive regex across `publishedContent.title`
and `publishedContent.summary`, which means the query reads every live article.
At 415 that is well under a second; if it ever stops being true the fix is a
wildcard text index or a generated n-gram field, not a longer regex - and note
that a wildcard index still only matches the *start* of a word, so true
substring search at scale needs the n-gram field. Two things this gives up:
- **No relevance.** A regex produces no score, so the chosen `sort` alone
  decides the order - searching sorted by date gives newest matches first, not
  best matches. Sorting by relevance meant an extra `$addFields` stage anyway,
  because Mongo will not sort a `$text` query by an ordinary field.
- **No stopwords.** `the` used to return nothing, because Mongo drops English
  stopwords before it searches. It now returns the 308 articles containing it.
  Nothing is dropped and the reader can narrow it down.

Every term is escaped with `escapeRegExp`, because a raw `(` or `.*` in a URL
would otherwise be regex syntax and match far more than anyone meant. Terms are
split on whitespace and each has to appear somewhere, so `old port` still finds
articles with both words rather than requiring them to be adjacent - that is what
`$text` did, and dropping it would have been a regression rather than a change.
`q` is capped at 80 characters, the same as the search box's `maxlength`, since a
hand-typed URL is the only way to exceed it. The text index is left in place: it
costs only disk, and it is the way back if the scan ever hurts.

**The pager shows five numbers around the reader, plus the first and last
page.** All 42 page numbers would be 42 buttons, and a reader on page 1 would
have to scroll past all of them. So `pageWindow(current, pages, span = 2)` in
`controllers/publicController.js` works out the window and marks the skipped
stretches as gaps, rendered as an ellipsis that is deliberately not a link. The
page being read is a `<span aria-current="page">` rather than a link to itself.
Previous and Next are unchanged, and `rel="prev"`/`rel="next"` stay on those two
only. `public/js/feed.js` holds a copy of `pageWindow` because a template cannot
require the controller - a browser copy is unavoidable for a redraw, and both are
checked against each other.

**One aggregation for the page, one for the count.** `$facet` would have saved a
round trip, but both of its branches run on the same already-sorted input, so
the count branch would re-sort the whole feed to count it. Two parallel
aggregations each do only their own work, and it is the pattern
`controllers/reporterController.js` already uses for its tab counts.

**The API projects its fields by name.** The feed pipeline ends with an explicit
`$project`. `draftContent` is the unapproved version and `editorNote` is between
the reporter and the editor - neither may reach a public endpoint, and a
hand-written API shape is exactly the place that mistake gets made.

**`?page=999` lands on the last page, not on an empty one.** A page number is
something anyone can type, so an out of range page is re-run against the last
real page. The cost is a second query, and only for a URL nobody meant to open.

**Unknown query values are dropped, not rejected.** `?sort=sideways`,
`?category=gossip` and `?page=-2` all fall back to defaults rather than erroring,
so an old link or a mistyped URL still lands on a working feed. Anything outside
the enums cannot reach Mongo as a filter.

**A view is one increment into one 5 minute bucket.** `services/viewCounter.js`
upserts on `{ article, bucketStart }`. The unique index on those two fields is
what makes the upsert safe, but two requests arriving together can both miss and
both try to create it, so a duplicate key error is caught once and retried as a
plain increment.

**`Article.viewCount` is not touched here.** It is a rollup of the buckets and
`docs/DECISIONS.md` is firm that it has to be aggregated on a cadence, not once
per view - one document per article would stay hot for the life of the article
while a bucket is replaced every 5 minutes. The seed fills it correctly, so
`sort=popular` works from the first run, and the ongoing rollup belongs to T4
along with the analytics page. Adding a timer in T1 would have put two people in
the same code.

**The view count is shown on the card and on the article page.** Both are plain
`viewCount` from the seed, thousands separated, and it needs no controller work:
the feed pipeline already projected `viewCount` for `sort=popular`, and
`findLiveArticle` returns the whole document. The number is formatted with
`toLocaleString('en-US')` in all three places - `views/feed.ejs`,
`views/article.ejs` and `public/js/feed.js` - on purpose. An unpinned
`toLocaleString()` would let a de-DE browser write `8.264` where the server wrote
`8,264`, and the number would change shape the moment a card is redrawn. Dates
are left unpinned; that is a separate question and not worth churning these lines
for.

**The counts do not move while you browse, and that is expected.** T1 only ever
writes buckets, so a number you see on the feed is the seed value until T4's
rollup exists. It sits oddly next to `?sort=popular`, where the order is by the
same frozen figure - but a live-looking counter here would mean writing
`viewCount` per view, which is exactly what `docs/DECISIONS.md` rules out.

**A failed view count must not break the article.** The increment is awaited, so
a count is not lost if the process goes, but it is wrapped and logged rather
than allowed to throw. A few milliseconds of analytics is not worth turning an
article a reader can see into a 500.

**A non-live article is a 404, worded the same as a wrong id.** `/article/:id`
and the two comment endpoints all answer "Article not found" for a missing
article *and* for one that is not live, so the public site cannot be used to
find out which articles exist while they are still with an editor.

**The body is plain text, split on blank lines.** `draftContent.body` is a
`String` and the reporter's editor is a bare `<textarea>` - there is no markdown
anywhere in the project. `toParagraphs()` splits on runs of blank lines and the
template escapes each one. Rendering it as HTML would need a sanitiser, and the
field has no reason to hold markup.

**Comments are capped at 100, keeping the newest.** The spec asks for no paging
on this endpoint, so a cap is what stops a heavily commented article handing a
guest an unbounded list. The newest hundred rather than the oldest hundred,
because the earliest 100 of 5000 is no use to anyone. The page says so when it
truncates.

**Comments are oldest first, form at the bottom.** New comments are appended
under the form, which is the order they were written in and where a reader
already is after submitting.

**Commenting needs JavaScript; reading does not.** The feed, the article and the
comments are all in the HTML, which is what the spec asks for. Posting is a JSON
endpoint and `docs/API.md` documents no page to redirect back to, so a
non-JS form post would land on raw JSON. Adding a redirect-after-post would have
meant deciding what a failed post looks like without JavaScript, and that is
more than the spec asks for. The form carries the same `maxlength` as the
`Comment` schema so the browser checks the obvious cases too.

**The feed JS reads the address bar, not a variable.** `public/js/feed.js` takes
its state from `location.search` and writes it back with `history.pushState`, so
a reload, a bookmark and the back button all mean the same thing with nothing
kept twice. Link clicks are intercepted from `data-` attributes rather than their
`href`, because a rendered `href` is a snapshot from the moment the page loaded
and goes stale as soon as the URL moves on without a reload.

**Client-side rendering uses `textContent`, never `innerHTML`.** Headlines,
summaries, bylines and comment bodies are all text someone typed. Every node is
built with `createElement` and `textContent`, so no value that comes back from
the API can bring markup with it.

**`feedLink()` resets the page rather than every call site remembering to.**
The helper takes the current query plus an override and drops defaults, so a
plain feed is `/` and a copied link is readable. Any change starts again at page
one unless the override names a page - which only the pager does.

## Running it

```
npm run seed
npm start
```

The seed is needed first: it creates the editor the login page needs, the
reporters, the images, 415 live articles and their view buckets.

## How to check it works

The repo has no test runner and no lint config, so this is manual. Nothing below
was run in the making of this branch - it is the list to work through.

Feed, with JavaScript on:

1. `http://localhost:3000` shows 10 cards, "415 articles", a pager reading
   `1 2 3 ... 42` with 1 marked as the current page, and the newest first.
2. Every card shows a view count with thousands separators, e.g. `8,264 views`.
3. Click **Most read** - cards reorder by view count, the chip goes active, the
   URL becomes `/?sort=popular`, and nothing reloads.
4. Type `port` in the search box - one request, cards narrow to 90 (it also finds
   "transport"), URL becomes `/?q=port`.
5. Type `por` instead - the same 90 articles. Part of a word is enough.
6. Type `the` - about 308 articles, so stopwords are searched like any other word.
7. Type `old port` - both words are found, they do not have to be adjacent.
8. Type `(` - no results, no error page. A regex metacharacter is a literal.
9. Click a category chip while a search is active - the search is kept, page
   resets to 1, the URL keeps both parameters.
10. Press the browser's back button - the previous feed comes back without a
    request to the server.
11. Click page **5**, then **20** - the numbers around the reader follow, the
    ellipses stay, and the page you are on is not a link to itself.
12. Click **Next** and confirm the URL, the pager and the cards all agree.
13. `http://localhost:3000/?page=99999` lands on page 42, not on an empty list.
14. `http://localhost:3000/?sort=sideways&category=gossip&page=-2` behaves
    exactly like `http://localhost:3000`.

Feed, with JavaScript off (devtools, or `curl http://localhost:3000/?q=port`):

15. The first page of results is in the HTML, and the form and the chips are
    ordinary links that navigate. The page numbers work the same way.

Article:

16. Any card's title opens `/article/:id` with the headline, byline, date, view
    count, image and the whole body in the HTML.
17. `curl http://localhost:3000/article/<a live id>` contains the body text.
    That is the spec's actual requirement, so it is worth checking by eye.
18. An article with `status: pending_editor` and `isLive: true` is still
    readable, and still shows its **published** text - not the draft.
19. An `isLive: false` id, and `not-a-real-id`, both give the 404 page.
20. An article that has been updated shows an "Updated" line; a never-updated
    one does not.
21. Browse a few articles, then go back to the feed. The counts have **not**
    moved, and `?sort=popular` still orders by the seed values. That is T4's
    rollup, not a bug.

Comments:

22. Comments are in the page HTML, oldest first, with the count in the heading.
23. Post one - it appears under the form without a reload, the count goes up,
    the body is cleared, the name is kept.
24. Post four quickly. The fourth answers `429` and the message about waiting
    appears in `#comment-error`. Reload and try again - the limit has gone.
25. `curl -X POST localhost:3000/api/articles/<live id>/comments -H
    'Content-Type: application/json' -d '{"authorName":"x","body":"y"}'`
    returns `201` and the new comment.
26. The same with an empty `body`, and with a 1001 character `body` - each
    answers `400` with a sentence rather than a Mongoose message.
27. `GET /api/articles/<not live id>/comments` gives `404`, so unapproved work
    cannot be commented on.

Views:

28. Every card and every article page shows a count with thousands separators,
    and it reads the same before and after a card is redrawn by the JavaScript.
29. Open one article, note `ViewBucket` for it, reload a few times, and check
    the current 5 minute bucket went up by the same amount. `ViewBucket.bucketFor`
    is the window; an old bucket will not move.
30. `Article.viewCount` should **not** change - that is T4's rollup. This is the
    one thing that looks broken and is not.

Things that should not happen:

31. `GET /api/articles?...` response never contains `draftContent`, `editorNote`
    or `status`, whatever you ask for.
32. No 500s in the server log while clicking through any of the above. The pager
    is the one to watch: `pageWindow` is passed into `views/feed.ejs` from
    `feedPage`, and forgetting that renders a 500 on every feed load.

## Open questions

- **Who owns `/api/weather`?** `docs/API.md` puts it in T1, `.env.example` says
  T4. It was agreed to leave it as a stub, but the two documents still disagree
  and one of them should change. It also needs a decision nobody has made: where
  the location comes from. OpenWeather needs a city or coordinates, and
  `OPENWEATHER_API_KEY` is empty in every `.env` so far.
- **The seed writes 415 live articles but `docs/API.md` promises a page of feed
  data without saying how many per page.** Ten is a choice, not a requirement.
- **Comment paging.** The 100 cap is a stopgap. If the spec wants the whole
  discussion, this endpoint needs a `page` parameter like the feed has.
